    Orden en el arranque de contenedores¶

    1. Introducción¶

    En una aplicación compuesta por varios servicios puede haber dependencias: una aplicación necesita conectarse a una base de datos, pero PostgreSQL puede tardar algunos segundos en estar operativo después de iniciar su contenedor.

    Sin dependencias explícitas, Compose puede arrancar los servicios sin garantizar que uno esté disponible antes que otro.

    Se debe diferencias entre un contenedor iniciado de un servicio preparado.

    2. Primer paso: depends_on¶

    La propiedad depends_on ayuda a definir el orden de creación, arranque y parada de servicios relacionados.

    En el siguinte ejemplo donde adminer depende de db, Compose arranca primero db (al detener o eliminar los servicios, tiene en cuenta el orden inverso).

    En ese caso el comando docker compose up arrancará los servicios en orden de dependencia: primero db, luego web. Y docker-compose stop los detendrá en el orden inverso.

    compose.yaml
    services:
  db:
    image: postgres:18
    environment:
      POSTGRES_USER: alumno
      POSTGRES_PASSWORD: clave_de_prueba
      POSTGRES_DB: tienda
    volumes:
      - pg_data:/var/lib/postgresql

  adminer:
    image: adminer:5
    environment:
      ADMINER_DEFAULT_SERVER: db
    ports:
      - "8080:8080"
    depends_on:
      - db

volumes:
  pg_data:

    2.1. ¿Qué problema sigue existiendo?¶

    El problema es que hay que distinguir:

    • Started / running: el contenedor está en ejecución.
    • Ready / preparado: el programa que se ejecuta dentro ya puede atender correctamente las operaciones que esperamos de él.

    Aquí es donde muchos desarrolladores tropiezan. depends_on (en su forma básica) solo espera a que el contenedor db esté en ejecución (running), pero no espera a que la aplicación dentro del contenedor esté lista (ready), en este caso que PostgreSQL esté preparado para recibir consultas.

    Una posible secuencia de fallo en una aplicación que necesita la base de datos en su arranque sería:

    1. Compose inicia el contenedor db.
    2. El contenedor pasa al estado running, aunque PostgreSQL continúe inicializándose.
    3. Compose inicia la aplicación que depende de db.
    4. La aplicación intenta conectarse antes de que la base de datos acepte conexiones.
    5. Si la aplicación no reintenta la conexión, puede fallar o finalizar.

    3. Solución: Usar healthcheck con depends_on¶

    Un healthcheck define una prueba que Docker ejecuta dentro del contenedor. A partir de su resultado, el contenedor puede aparecer como starting, healthy o unhealthy.

    Si utilizamos la forma larga de depends_on con condition: service_healthy, Compose espera a que esa prueba indique un estado saludable antes de crear o iniciar el servicio dependiente.

    Esta es la forma más limpia y moderna de hacerlo si usas docker-compose.yml. Le dices a Docker Compose cómo comprobar la salud del contenedor de la base de datos y haces que tu aplicación espere a que esa comprobación sea exitosa.

    1. Se añade una clave healthcheck al servicio de PostgreSQL yaml healthcheck: test: ["CMD-SHELL", "pg_isready -h 127.0.0.1 -U \"$${POSTGRES_USER}\" -d \"$${POSTGRES_DB}\""] interval: 5s timeout: 3s retries: 10 start_period: 20s

    2. Usar la condición service_healthy en depends_on de al aplicación que use la BD 

          depends_on:
      db:
        condition: service_healthy

    En el healthcheck se utiliza pg_isready (utilidad incluida en la imagen de PostgreSQL) para comprobar si el servidor acepta conexiones. Los parámetros adicionales son:

    • interval: 5s: intervalo entre comprobaciones.
    • timeout: 3s: tiempo máximo permitido para una comprobación.
    • retries: 10: cantidad de fallos consecutivos antes de considerar unhealthy un contenedor después del período inicial.
    • start_period: 20s: período de gracia inicial durante el cual los fallos no agotan el contador de reintentos; una prueba con exito puede terminar esa espera.

    El fichero completo

    compose.yaml
    services:
  db:
    image: postgres:18
    environment:
      POSTGRES_USER: alumno
      POSTGRES_PASSWORD: clave_de_prueba
      POSTGRES_DB: tienda
    volumes:
      - pg_data:/var/lib/postgresql
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -h 127.0.0.1 -U \"$${POSTGRES_USER}\" -d \"$${POSTGRES_DB}\""]
      interval: 5s
      timeout: 3s
      retries: 10
      start_period: 20s

  adminer:
    image: adminer:5
    environment:
      ADMINER_DEFAULT_SERVER: db
    ports:
      - "127.0.0.1:8080:8080"
    depends_on:
      db:
        condition: service_healthy

volumes:
  pg_data:

    Puede observar que al desplegar el contenedor de la base de datos no indica Created sino Healthy

    $ docker compose up -d
[+] up 4/4
 ✔ Network v02_default     Created         0.0s
 ✔ Volume v02_pg_data      Created         0.0s
 ✔ Container v02-db-1      Healthy         5.9s
 ✔ Container v02-adminer-1 Started         6.0s
$

    ¿Por qué escribimos $${POSTGRES_USER}?

    En un archivo Compose ${POSTGRES_USER} haría que Compose intentara sustituir la variable desde el entorno del anfitrión o desde .env. Eso no es lo que queremos: POSTGRES_USER está ya definida dentro del contenedor.

    Con $${POSTGRES_USER} escapamos el signo $ para que Compose deje la expresión destinada al shell del contenedor. El mismo criterio se aplica a $${POSTGRES_DB}.

    Obtener el estado de salud

    Para obtener el estado de salud del contenedor db 

    docker inspect \
       --format '{{.State.Health.Status}}' \
       "$(docker compose ps -q db)"
    o 
    docker inspect \
       --format '{{json .State.Health}}' \
       "$(docker compose ps -q db)" \
       | json_pp
