    Complementos y ayudas¶

    En este apartado aprenderá a

    • separar la configuración del archivo Compose y a
    • construir una imagen en un compose a partir de un Dockerfile.

    1. compose y variables de entorno¶

    Las variables de entorno permiten cambiar contraseñas, nombres de bases de datos o puertos sin editar constantemente el fichero compose.yaml.

    Hay dos operaciones distintas:

    Operación ¿Para qué sirve? Ejemplo
    Interpolación Sustituir expresiones en el archivo Compose antes de crear los contenedores. image: "postgres:${PG_VERSION}"
    Entorno del contenedor Proporcionar variables que leerá el proceso ejecutado dentro del contenedor. POSTGRES_DB=tienda

    No son equivalentes

    Que exista una variable en .env no significa que se copie automáticamente al contenedor. Para introducirla en su entorno debes utilizar la clave environment o env_file.

    1.1. Utilizar fichero .env¶

    Vamos a crear un directorio de trabajo con estos dos archivos, .env y compose.yaml: 

    postgres-env/
├── .env
└── compose.yaml

    El conteniodo del primero:

    .env
    PG_USERNAME=alumno
PG_PASSWORD=clave_de_prueba
PG_DATABASE=tienda
ADMINER_PORT=8080

    Las variables de .env pueden utilizarse en compose.yaml con la sintaxis ${VARIABLE}:

    compose.yaml
    services:
  db:
    image: postgres:18
    environment:
      POSTGRES_USER: ${PG_USERNAME}
      POSTGRES_PASSWORD: ${PG_PASSWORD}
      POSTGRES_DB: ${PG_DATABASE}
    volumes:
      - pg_data:/var/lib/postgresql

  adminer:
    image: adminer:5
    environment:
      ADMINER_DEFAULT_SERVER: db
    ports:
      - "${ADMINER_PORT:-8080}:8080"

volumes:
  pg_data:

    Observe que en este caso algunas de las variables de entorno del fichero .env

    • se pasan al contenedor usando la clave enviromenty se mapean a variables del fichero compose con nombres diferentes como por ejemplo POSTGRES_USER: ${PG_USERNAME}.
    • se interpolan en claves del fichero compose, pe. ADMINER_PORT

    Puede validar el fichero con docker compose config -q (valida y no imprime nada) o docker compose config (se muestra el fichero con las variables ya interpoladas).

    valor por defecto

    La expresión 

      - ${ADMINER_PORT:-8080}:8080"
    hace que si la variable ADMINER_PORT no está definida en el fichero .env tome el valor por defecto 8080.

    persistencia

    Las variables POSTGRES_USER, POSTGRES_PASSWORD y POSTGRES_DB se aplican durante la inicialización de un directorio de datos vacío. Cambiar .env después no modifica automáticamente un usuario o una contraseña que ya existan en la base de datos.

    1.2. Usando la clave: env_file¶

    En el ejemplo anterior se incluyen las variables que necesite del fichero y se interpolan a las variables que necesite.

    Otra posibilidad es pasarle a un servicio todas las variables definidas en un archivo. Para este nuevo ejemplo cree un fichero .env.db:

    .env.db
    MARIADB_ROOT_PASSWORD=example
MYSQL_ROOT_PASSWORD=clave-aula
MYSQL_DATABASE=aula
MYSQL_USER=alumno
MYSQL_PASSWORD=clave-alumno

    Y use por ejemplo este compose. Observe la nueva clave env_file:

    services:
  db:
    image: mariadb
    env_file:   # nueva clave
    - .env.db   # Fichero con variables de entorno para contenedor
    volumes:
      - mysql_datos:/var/lib/mysql

  adminer:
    image: adminer:5
    ports:
      - 8080:8080

volumes:
  mysql_datos:

    Observe que en este caso las variables de entorno del fichero .env.db deben tener el mismo nombre que las variables que espera la imagen del fichero compose, sus nombres deben ser los que entiende la imagen oficial.

    Diferencia esencial

    • .env suele utilizarse como fuente de valores para la interpolación de ${VARIABLE}.
    • env_file es una propiedad de un servicio y entrega las variables de ese archivo al contenedor.
    • environment también entrega variables al contenedor y, si ambas opciones definen la misma variable, prevalece environment.
    • Un archivo puede llamarse .env y aparecer también bajo env_file, pero son dos mecanismos diferentes.

    Las contraseñas pueden aparecer en pantalla

    El archivo .env no cifra los secretos: solo separa la configuración del YAML. docker compose config, docker compose config --environment y docker inspect pueden mostrar valores sensibles. Evita copiar su salida en capturas o repositorios públicos.

    2. compose con build¶

    Hasta ahora Compose ha utilizado imágenes existentes mediante image:. Con build: podemos construir nuestra propia imagen a partir de un Dockerfile.

    Nos creamos un proeyecto como este:

    apache-build/
├── compose.yaml
├── Dockerfile
└── html/
    └── index.html

    El index podría ser

    html/index.html
    <!doctype html>
<html lang="es">
<head>
  <meta charset="utf-8">
  <title>Apache con Compose</title>
</head>
<body>
  <h1>Mi imagen personalizada de Apache</h1>
</body>
</html>
    El fichero de construcciñon de la imagen

    Dockerfile
    FROM httpd:2.4
COPY ./html/ /usr/local/apache2/htdocs/

    Y el compose:

    compose.yaml
    services:
  web:
    build:
      context: .
      dockerfile: Dockerfile # no necesario si nombre y ruta ok
    image: aula-apache:1.0
    ports:
      - "127.0.0.1:8086:80"

    Aquí

    • build.context indica el directorio desde el que se envían los archivos necesarios para construir la imagen,
    • y build.dockerfile indica qué archivo contiene las instrucciones de construcción. Si el fichero se llama Dockerfile y está en la raíz del contexto, también basta build: ..

    Para probarlo:

    docker compose config -q
# Construir la imagen definida por build
docker compose build

docker compose up -d
curl http://localhost:8086

    Si modifica el texto de html/index.html tendrá que construir y desplegar, y para eso puede añadir al despliegue la opción --build:

    docker compose up -d --build

    build no es similar al uso de un volumen

    El COPY del Dockerfile incluye los archivos en la imagen en el momento de construirla. Si editas html/index.html, necesita reconstruir la imagen. En cambio con un montaje volumes: - ./html:/usr/local/apache2/htdocs:ro los cambios en el directorio del anfitrión suelen verse directamente sin crear otra imagen.
