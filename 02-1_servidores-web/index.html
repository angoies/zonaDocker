    Servidores Web

    Una vez que conoce el funcionamiento básico de la tecnología de contenedores puede desplegar servicios (servidores web, bases de datos, gestores de contenidos, etc.) de una forma rápida y sencilla.

    1. Uso básico: servidor Apache¶

    La imagen oficial httpd incorpora el servidor Apache HTTP Server. Descarga y ejecuta una versión explícita de la rama 2.4:

    docker run -d --name web-basica -p 127.0.0.1:8081:80 httpd:2.4
    • -d: ejecuta el contenedor en segundo plano.
    • --name: asigna un nombre al contenedor.
    • -p 8081:80: enlaza el puerto 8081 del anfitrión**con el **80 del contenedor.
    • httpd:2.4: indica la imagen y su etiqueta. La rama 2.4 recibe actualizaciones; para máxima reproducibilidad se podría fijar también un digest.

    Comprueba el servicio con los comandos:

    docker ps
curl http://localhost:8081/
docker logs web-basica

    En el navegador: http://localhost:8081/. La respuesta típica de la página de bienvenida de la imagen es It works!.

    docker run -d --name web-basica -p 127.0.0.1:8081:80 httpd:2.4

    Navegadores y la caché

    Los navegadores web a veces hacen una gestión "anómala" de la cache. Para evitar problemas puede invocar el navegador en modo privado o de incognito. En el caso de firefox sería con la opción --private-window

    $ firefox --private-window localhost

    Usar 127.0.0.1 delante del puerto?

    Es posible al lanzar el contenedor y mapear el puerto indicar la IP del host o anfitrión que expondrá dicho puerto. Si no se indica se expone en todas las interfaces. Si quiere limitar las pruebas puede lanzar elcontenedor con al opción -p 127.0.0.1:8081:80. En ese caso enlaza el puerto 8081 del anfitrión, únicamente en su interfaz local,

    ```bash
docker run -d -p 127.0.0.1:8081:80 httpd:2.4
```

    2. Nombres locales¶

    Si no puede modificar el fichero /etc/hosts

    Si no puede modificar el fichero /etc/hosts tiene dos opciones

    • usar el "dominio" .localhost que resuelve por defecto a 127.0.0.1 y es lo que haremos en general en als prácticas en local.
    • Usar una máquina virtual donde tenga permisos para las prácticas

    2.1. .localhost¶

    Observe un ejemplo con sitio1.localhost:

    $ curl sitio1.localhost
...
<title>It works! Apache httpd</title>
</head>
<body>
<p>It works!</p>
...
$

    Y otro con un subdominio sitio1.midominio.localhost

    $ curl sitio1.midominio.localhost
...
<title>It works! Apache httpd</title>
</head>
<body>
<p>It works!</p>
...
$

    Comprobar compatibilidad

    No todos los programas y sistemas resuelven nombres como sitio1.localhost de la misma forma. Si curl no resuelve ese nombre en un equipo, utiliza localhost o prueba con el navegador. No confundas .localhost (acceso al propio equipo) con el DNS interno de Docker Compose (nombres de servicio entre contenedores).

    2.2. /etc/hosts¶

    Si tiene permisos de administrador podría modificar el fichero /etc/hosts para "simular" resolución de nombres y crear un dominio sitio1.internal (sobre el uso de TLDs privados). Edite y añada una línea en dicho fichero similar a 127.0.0.1 sitio1.internal

    alu@xd13:~/DW/apache$ sudo nano /etc/hosts
...
alu@xd13:~/DW/apache$ cat /etc/hosts
127.0.0.1   sitio1.internal
127.0.0.1   localhost
...
alu@xd13:~/DW/apache$

    Y ahora puede usar el nombre del dominio "creado":

    $ curl sitio1.internal

    3. Servir un sitio web personalizado: bind mount¶

    La imagen httpd sirve los archivos de /usr/local/apache2/htdocs/ (consultar documetnación en DockerHub). Puede montar ahí un directorio del anfitrión para editar la web sin reconstruir la imagen.

    Cree esta estructura con un fcihero html y su hoja de estilos:

    servidor-web/
└── html/
    ├── index.html
    └── css/
        └── estilos.css

    Para ejecutar y probar basta hacer un bind mount de html a /usr/local/apache2/htdocs/ añadiendo la opción -v ./html:/usr/local/apache2/htdocs/. Lanza Apache desde el directorio servidor-web:

    docker run -d --name web \
  -p 8081:80 \
  -v ./html:/usr/local/apache2/htdocs/ \
  httpd:2.4

    Y se comprueba 

    $ docker ps
$ curl http://localhost:8081/

    Bind mounts

    La carpeta html debe existir antes del montaje. El sufijo readonly impide que el contenedor modifique los archivos del sitio. Los cambios que haga en el editor del anfitrión se verán normalmente al recargar el navegador. Si no aparece el cambio, revise la caché.

    3.1. Usando fichero compose¶

    Y para ahcer más manejable el despliegue puede crear un fichero compose. Cree el fichero en servidor-web:

    compose.yaml
    services:
  apache:
    image: httpd:2.4
    ports:
      - "127.0.0.1:8081:80"
    volumes:
      - ./html:/usr/local/apache2/htdocs:ro
    restart: unless-stopped

    docker compose config       # Valida y muestra la configuración interpretada
docker compose up -d
docker compose ps
curl http://localhost:8081/
docker compose logs apache

    Compose asigna nombres y organiza los recursos por proyecto. El directorio del proyecto ayuda a identificar los servicios, redes y volúmenes.

    docker compose stop          # Detiene sin eliminar
docker compose start         # Vuelve a iniciar
docker compose down          # Elimina servicios y red de este proyecto

    down no elimina el directorio html, puesto que está en el anfitrión.

    4. Imagen con la aplicación¶

    Un bind mount es práctico durante el desarrollo, pero para distribuir un sitio estático, puede ser preferible construir una imagen propia que contenga los archivos. En la misma carpeta, cree:

    Dockerfile
    FROM httpd:2.4
COPY ./html/ /usr/local/apache2/htdocs/

    Ahora basta construir la imagen y probarla:

    docker build -t miweb:1.0 .
docker run -d --name web-imagen -p 8081:80 miweb:1.0
curl http://localhost:8081/
docker rm -f web-imagen
