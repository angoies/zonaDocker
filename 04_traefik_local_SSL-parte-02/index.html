    HTTPS con Traefik: segunda parte¶

    1. Certificados wildcard¶

    En la práctica previa hemos creado:

    whoami.alumno01.freemyip.com
        │
        └── certificado propio
nginx.alumno01.freemyip.com
        │
        └── certificado propio

    Si añade muchos servicios necesitará muchos certificados. Buscamos utilizar un certificado comodín del tipo:

    *.alumno01.freemyip.com

    que cubra:

    whoami.alumno01.freemyip.com
nginx.alumno01.freemyip.com
apache.alumno01.freemyip.com
wordpress.alumno01.freemyip.com
tomcat.alumno01.freemyip.com
etc

    El certificado *.alumno01.freemyip.com cubre nombres de un nivel como:

    whoami.alumno01.freemyip.com
nginx.alumno01.freemyip.com

    pero no cubre:

    alumno01.freemyip.com
www.nginx.alumno01.freemyip.com

    Por este motivo suele interesar solicitar conjuntamente estos dos cerctifiados:

    alumno01.freemyip.com
*.alumno01.freemyip.com

    wildcard y desafios

    Let's Encrypt permite emitir certificados wildcard mediante DNS-01. No es posible obtener un wildcard mediante HTTP-01 o TLS-ALPN-01.

    1.1. Preparación¶

    fichero .env

    Se supone tiene el fichero .envde la practica previa con las variables de entorno necesarias para el compose. Y que carga dichas variables mediante la secuencia

    set -a
source .env
set +a
echo $DOMAIN $FREEMYIP_TOKEN

    Debe detener el proyecto anterior si estaba activo, hacer copia del compose, guardar el almacenamiento de certificados anterior, y crear uno nuevo

    docker compose down
cp compose.yml compose-inicial.yml
mv letsencrypt/acme.json letsencrypt/acme-individual.json
touch letsencrypt/acme.json
chmod 600 letsencrypt/acme.json

    Modo de pruebas o staging

    Vamos a segir trabajando en el modo Staging.

    1.2. Modificar traefik¶

    Edite el fichero y en el servicio Traefik añada las líneas que se muestran:

      - "--entrypoints.websecure.http.tls.certresolver=le"
  - "--entrypoints.websecure.http.tls.domains[0].main=${DOMAIN}"
  - "--entrypoints.websecure.http.tls.domains[0].sans=*.${DOMAIN}"

    Con esas líneas ahora se indica:

    • Todos los routers que utilicen websecure tendrán TLS activado y utilizarán por defecto el resolver le.
    • Solicita certificados para el dominio y el wildcard.

    La parte relevante del servicio quedaría:

      command:
    # Parte omitida

    # Parte añadida para wildcard
    - "--entrypoints.websecure.http.tls.certresolver=le"
    - "--entrypoints.websecure.http.tls.domains[0].main=${DOMAIN}"
    - "--entrypoints.websecure.http.tls.domains[0].sans=*.${DOMAIN}"

    # Resolver ACME
    - "--certificatesresolvers.le.acme.email=${LE_EMAIL}"
    - "--certificatesresolvers.le.acme.storage=/letsencrypt/acme.json" 

    # Parte omitida

    Esto implicará cambios en los servicios que se ven a continuación.

    1.3. Simplificar los routers¶

    En la configuración de certificados individuales en cada servicio se añadían estas dos líneas:

    - "traefik.http.routers.whoami.tls=true"
- "traefik.http.routers.whoami.tls.certresolver=le"

    Ahora esas líneas no son necesarias porque tls y el certresolver están asociados al entryPoint.websecure.

    El servicio whoami queda ahora:

      whoami:
    image: traefik/whoami
    labels:
      - "traefik.enable=true"
      - "traefik.http.routers.whoami.rule=Host(`whoami.${DOMAIN}`)"
      - "traefik.http.routers.whoami.entrypoints=websecure"
      # Se omiten en configuración wildcard
      # - "traefik.http.routers.whoami.tls=true"
      # - "traefik.http.routers.whoami.tls.certresolver=le"

    1.4. Lanzar el proyecto¶

    Revisar compose.yml

    Se supone para este ejemplo que sólo tiene el whoami. Si tiene otros servicios en el fichero de despliegue debe comentarlos.

    Lanzamos el proyecto y revisamos el log:

    docker compose up -d
docker compose logs -f traefik

    1.5. Comprobar certificados¶

    Puede comprobar en el log que Traefik solicitará certificados con nombres similares a:

    alumno01.freemyip.com
*.alumno01.freemyip.com

    Y si ejecuta el comando

    openssl s_client \
  -connect 127.0.0.1:443 \
  -servername whoami.${DOMAIN} \
  </dev/null 2>/dev/null |
openssl x509 -noout -subject -issuer -ext subjectAltName

    Deberías encontrar algo similar a

    ...
X509v3 Subject Alternative Name: 
    DNS:*.alumno01.freemyip.com, DNS:alumno01.freemyip.com

    Y si muestra el fichero acme.json verá algo similar a

    $ more letsencrypt/acme.json
...
"Certificates": [
      {
        "domain": {
          "main": "midominio.freemyip.com",
          "sans": [
            "*.midominio.freemyip.com"
          ]
        },
        "certificate":

    1.6. Probar el servicio¶

    curl -Lk whoami.midominio.freemyip.com

    1.7. Utilidad del wildcard¶

    Si añade después un servicio nuevo como apache y además descomenta el servicio nginx (y recuerde que debe eliminar las dos líneas tls)

      nginx:
    image: nginx:alpine
    labels:
      - "traefik.enable=true"
      - "traefik.http.routers.nginx.rule=Host(`nginx.${DOMAIN}`)"
      - "traefik.http.routers.nginx.entrypoints=websecure"

  apache:
    image: httpd:alpine
    labels:
      - "traefik.enable=true"
      - "traefik.http.routers.apache.rule=Host(`apache.${DOMAIN}`)"
      - "traefik.http.routers.apache.entrypoints=websecure"

    Ejecuta:

    docker compose up -d nginx apache

    Y accede a:

    curl -Lk nginx.midominio.freemyip.com
curl -Lk https://apache.midominio.freemyip.com
firefox https://apache.midominio.freemyip.com

    Puede comprobar que no ha sido necesario emitir un certificado específico para nginx ni apache. Compruébalo mediante:

    openssl s_client \
  -connect 127.0.0.1:443 \
  -servername apache.${DOMAIN} \
  </dev/null 2>/dev/null |
openssl x509 -noout -serial -ext subjectAltName

    Que da la misma salida que en el partado previo (ver serial). Puede también visualizar el fichero de certificados, que ni siquera ha sido modificado.

    2. Opcional: Certificados reales¶

    Una vez comprobado que todo funcione con el modo de pruebas o Staging puede optar por una configuración real con certificados válidos.

    En el aula

    Tenga en cuenta que en el aula todos salimos al exterior con la misma IP. Si hay demasidas peticiones desde la misma IP puede ser que Let's Encrypt limite el servicio.

    2.1. Preparación¶

    Detener el despligue y hacer una copia del fichero con los certificados obtenidos en Staging y cree un fichero nuevo:

    docker compose down
mv letsencrypt/acme.json letsencrypt/acme-staging-wildcard.json
touch letsencrypt/acme.json
chmod 600 letsencrypt/acme.json

    2.2. Modificar compose¶

    En el fichero compose.yml comenta la línea:

    - "--certificatesresolvers.le.acme.caserver=https://acme-staging-v02.api.letsencrypt.org/directory"

    La configuración quedará utilizando el servidor ACME de producción de Let's Encrypt.

    No repitas este paso innecesariamente

    Let's Encrypt aplica límites de emisión. No borres continuamente acme.json para volver a solicitar los mismos certificados.

    2.3. Lanzar el proyecto¶

    Lanza el proyecto y comprueba en el log la obtención de los certificados. Traefik solicitará ahora certificados públicos reales.

    docker compose up -d
docker compose logs -f traefik

    Observa el procesode obtención del certificado, Busca en el log certificate, domain, dns.01, etc.

    2.4. Comprobar certificados¶

    Puede comprobar que todo es correcto usando curl sin la opción -k

    curl -L  http://apache.${DOMAIN}
curl     https://whoami.${DOMAIN}

    o en el navegador que ahora el navegador debería aceptar los certificados sin mostrar una advertencia de confianza:

    firefox --private-window  https://nginx.${DOMAIN} &
firefox --new-window  http://whoami.${DOMAIN} &

    Puede obtener información de los certificados:

    openssl s_client \
  -connect 127.0.0.1:443 \
  -servername whoami.${DOMAIN} \
  </dev/null 2>/dev/null |
openssl x509 -noout -subject -issuer -dates -serial
